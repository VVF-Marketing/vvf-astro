## Context

See proposal.md (Why) for the problem. Constraints found in EmDash 0.38:

- **Sidebar:** each collection has `group` (one folder level), `sortOrder`, `hidden`, `label`, `labelSingular`, `description`, `admin.listColumns`, `titleField` and `dateField`. The admin draws no icon per collection: `getCollectionNavIcon` keys on built-in names only.
- **List order:** every content list defaults to `dateField` descending, or `updatedAt` descending when there is no `dateField`. Users can re-sort by column. There is no "default sort by field X" setting.
- **Re-seeding is unsafe.** `emdash seed --on-conflict update` updates collections and fields, but it also re-applies `settings` and clears and recreates menu items. On a live CMS that wipes marketing's menu and settings edits, so it can't be the upgrade path.
- **Schema writes need `schema:write`.** `EMDASH_SYNC_PAT` has only `content:read` + `content:write`.
- **Current storage:** one `page_copy` collection, 20 manifests (19 page/template routes plus `_global`), ~650 slots per locale. Rows are keyed by `route_path` + `key`, Spanish rows are linked by `translation_group`, and `titleField` is `label`.
- **Readers of `page_copy`:**
  - `getPageCopy` / `storedSlots` (`src/lib/content/index.ts`)
  - `syncSlots` (`src/lib/staticPageSync.ts`)
  - the guard's slot rule (`src/lib/marketingGuard.ts`)
  - `pageCopyEntries` (`scripts/migrate/transform.mjs`)
  - `importCopy` (`scripts/migrate/importcopy.mjs`)
  - `e2e/drafts.spec.ts`

## Goals / Non-Goals

**Goals:**
- One source of truth for the sidebar (folders, names, descriptions, order, hidden), used by the seed, the upgrade script and a CI check.
- Copy storage per manifest, without changing how pages declare or render copy (`getPageCopy(manifest, locale)` keeps its signature).
- A safe, re-runnable upgrade for existing databases.

**Non-Goals:**
- Forking or patching the EmDash admin, or adding nested folders, custom admin pages or per-collection icons.
- Changing which slots exist, their text, or their limits.
- Renaming collection slugs other than `page_copy`. Labels change; `campaign_settings`, `campaign_updates` and `children` keep their slugs, so code, the guard and the MCP keep working.
- Carrying `page_copy` revision history over (see Risks).

## Decisions

### D1. One navigation config module
`src/lib/cmsNavigation.mjs` is plain ESM, so Node 22 scripts and CI can import it, as `site.mjs` already is. It declares:
- the folders, in order: `Pages & SEO`, `CMS collections`, `Banner`;
- **copy pages**: an ordered list of `{ route, name, description }`. Main-menu order comes first, then the other pages, then shared-text entries, with `_global` ("Site-wide text") last. Array order becomes `sortOrder`.
- **content collections**: `{ slug, label, labelSingular, description, group, sortOrder, listColumns }`, plus `hidden: ['pages']`;
- `copyCollectionFor(route)`: a deterministic slug, `copy_` plus the route with non-alphanumerics turned into `_`. `/` becomes `copy_home`, `/events/*` becomes `copy_events_detail` and `_global` becomes `copy_site`. All fit the `^[a-z][a-z0-9_]*$` / 63-char rule.

**Rejected alternatives:**
- A `name` argument on every `defineCopy`: this scatters sidebar order across 20 files and leaves the content collections elsewhere.
- Writing the settings straight into `seed/seed.json`: it's regenerated by `transform.mjs`, and the upgrade script would need its own copy.

A unit test fails when:
- a manifest has no copy-page entry, or an entry has no manifest;
- a seed collection is in neither a folder nor `hidden`.

### D2. Per-manifest copy collections with the same field set
Each copy collection has the `page_copy` fields minus `route_path`, which the collection now implies, plus:
- `section`: select `seo` | `content`, derived from the key: `seo.*` is SEO, everything else is Content.
- `title`: string, the shown title, e.g. "01 · SEO · Title". `titleField` points to it, so `label` stays the plain code label used in guard messages.
- `position`: integer, the slot's number on the page (SEO first, then content, each in declaration order), also shown in the title.

`supports: ['drafts', 'revisions']`, `routable: false`, `translatable: false` on everything except the value fields, as today. `value` is `searchable`, so the admin list's search box finds a slot by its text. EmDash only shows single-line fields (`string`, `number`, `select`…) as list columns, so the multi-line `value` can't be a column (found on the user's dev server; decided with the user on 2026-10-04: search instead of a preview field that would go stale).

The read path becomes `queryLocale(copyCollectionFor(manifest.route), { limit: 500 }, locale)`. There's no `where` clause any more, and it's still two queries per page (page + global). When the collection doesn't exist, the read returns no rows and the page renders its defaults, as it does today for an empty slot.

**Rejected:** keeping one `page_copy` and only improving titles. That's cheaper, but it can't give the Page level in the sidebar the user asked for.

### D3. SEO first, then page order, by sorting on Title
EmDash lists entries by `dateField` (or `updatedAt`) descending and has no setting for another default order. The Date column is always labelled "Date" and shows the field's value. Spike 1.1 confirmed that a synthetic ordering date would show every slot with a meaningless date. Instead, each slot's title starts with its number on the page: SEO slots first in declaration order, then content slots in declaration order, zero-padded to the collection's width (two digits, three for "Site-wide text"). Examples are "01 · SEO · Title" and "04 · Content · Hero heading". Clicking the Title column (sortable because it's the collection's `titleField`, which EmDash adds to the sortable fields) gives page order. The default view stays "recently updated", which is useful for reviewing recent edits. The marketing guide tells editors to click Title. Decided with the user on 2026-10-04.

**Rejected:**
- A synthetic `list_order` datetime as `dateField`: the default order is right, but the Date column would show fake dates.
- Plain section prefixes: they sort Content before SEO and alphabetically within a section.
- Relying on `updatedAt`: every edit reshuffles the list.

### D4. Schema-only apply script instead of re-seeding
`scripts/cms-schema.mjs` (`npm run cms:schema`) reads D1 and the field definitions and calls EmDash's schema API with an **admin** token (`EMDASH_ADMIN_TOKEN`, `schema:read` + `schema:write` + `content:*`, used only by hand or by the deploy step). It:
- creates missing copy collections and fields;
- updates label, labelSingular, description, group, sortOrder, hidden, listColumns, titleField and dateField on every configured collection;
- never touches menus, settings or content values.

It is idempotent (compare first, write only differences) and prints a dry-run diff with `--dry-run`. `transform.mjs` emits the same collections into `seed/seed.json`, so fresh databases (CI, `npm run seed`) match.

**Rejected:**
- `emdash seed --on-conflict update`: it wipes menus and settings.
- Giving the sync `schema:write`: the always-on token gets broader than it needs, and a request could alter the schema.

### D5. Sync stays content-only
`syncSlots` loops per manifest over `copyCollectionFor(route)`. It keeps today's rules (create missing per locale, update metadata on English only, never overwrite values or publish over drafts, flag stale, dedupe) and adds `title`, `section` and `position` to the synced metadata. A missing collection goes into a new `collectionsMissing` result field and is logged, and the run continues. The `pages` inventory sync is unchanged.

### D6. One-time `page_copy` migration
`scripts/migrate/copy-collections.mjs` (`npm run migrate:copy-collections`) runs after `cms:schema`, with the admin token. For each `page_copy` English row and each declared slot, it creates the row in the page's collection, then the Spanish row with `translationOf`.
- Values come from the **published** row data.
- An open draft on the old row is re-created as a draft on the new row: create, publish the published value, then update without publishing.
- Rows already present (matched by `key`) are skipped, which makes the migration re-runnable.

When every declared slot is present in its new collection, it sets `page_copy` to `hidden` and reports. Deleting `page_copy` is a follow-up after one release. `importCopy` and `pageCopyEntries` switch to the per-page collections.

### D7. Guard
- `marketingGuard` replaces `collection === 'page_copy'` with `isCopyCollection(collection)`, a slug in the config's copy-page list.
- `slotEditProblem` treats `title`, `section` and `position` as structural, so only the value field may change.
- Schema-writing MCP tools and REST `/schema/*` writes are already refused by deny-by-default. They get explicit tests so a future allowlist edit can't open them.

### D8. Renames are labels only
| Slug | New label | Field label changes |
|---|---|---|
| `campaign_settings` | "Site banner" | `active` → "Show the banner", `banner_text` → "Banner text (shown at the top of every page)" |
| `campaign_updates` | "Earthquake relief updates" | none |
| `children` | "Children" | none |

## Risks / Trade-offs

- **[`page_copy` revision history isn't migrated]** → The site isn't live on EmDash yet. The migration keeps current published values and open drafts. `page_copy` stays hidden, not deleted, for one release, so history is still readable.
- **[Twenty copy collections clutter MCP collection lists for AI clients]** → Each description names the page and its address, and the marketing guide gives the MCP prompt pattern ("in the Ways to Give copy collection…").
- **[A new page needs `cms:schema` before its copy is editable]** → The page still renders defaults. The sync reports the missing collection on every start, and CI's config test fails if the page isn't in `cmsNavigation.mjs`. The deploy checklist runs `cms:schema`.
- **[Editors must click Title to see page order]** → It's the first step in the guide's "editing a page" section. The default "recently updated" view is useful for reviewing edits.
- **[Admin token handling]** → Used only for the two scripts, never stored in the repo or in the running server's environment. The docs follow the existing token rules.
- **[Label renames confuse people used to the old names]** → They're in the marketing guide's sidebar map. Slugs, URLs and MCP collection names don't change.

## Migration Plan

Once per environment, running the commands from a checkout of the new code pointed at the environment with `EMDASH_URL`:

1. `npm run cms:schema -- --dry-run`, review, then `npm run cms:schema`.
2. `npm run migrate:copy-collections` moves `page_copy` values, drafts and Spanish versions, then hides `page_copy`.
3. Deploy the code. Its sync fills any slot rows still missing when it starts.
4. Spot-check Pages & SEO › Home in both locales and one Spanish page on the site.

Steps 1 and 2 only add collections and hide `page_copy`, which the running (old) code keeps reading, so visitors see no change until the deploy. Pause copy edits from step 2 until step 3: edits to the hidden `page_copy` would be lost, and edits in the new collections only show after the deploy. Deploying first instead would show every page's default copy until the migration ran.

**Rollback:** redeploy the previous code, which reads `page_copy`, untouched apart from `hidden`. Un-hide `page_copy`. The new collections can stay; they're unused. Copy edited in the new collections after the deploy isn't in `page_copy`, so a rollback drops it unless it's re-entered.
